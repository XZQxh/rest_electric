# 可行性分析

## 实测结论（2026-10-22 更新）

| 问题 | 结果 |
|---|---|
| 能否在微信之外复现请求 | **能**。Python 直接 POST 返回 200，余额 24.1 |
| 是否有证书固定 | 无 |
| 是否有额外签名/加密 | 无，只需 `sw-Authorization: Bearer <JWT>` |
| token 有效期 | **2 小时**（JWT exp 实测），服务端不续发 |
| 网络可达性 | 仅校园网（`172.18.3.170`） |
| 结论 | 路线 A 技术成立，**但 2 小时 token 让「每天自动查」暂时不成立** |

一句话：**抓包这一关过了，"无人值守"这一关还没过。** 下一步不是写代码，而是搞清 token 怎么自动续。

## 原先的判断（保留作记录）

## 一句话结论

**「每天记录余额 + 阈值告警 + 上树莓派」这套工程实现是确定的、没有悬念的**；全部技术风险集中在一件事上：**能不能在微信之外复现小程序对后端的查询请求**。抓一次包就能定生死。

---

## 1. 为什么风险只集中在一个点

小程序的登录链路决定了这一点：

```
小程序内点击查询
   └─ wx.login()  → 得到一次性 code（只能由微信客户端生成）
        └─ 后端 /login { code }  → openid → 下发业务 token
             └─ 查询接口带 token → 返回余额
```

- 第一步的 `code` **无法在树莓派上伪造**（需要微信客户端 + appid 对应的会话）。所以「服务器自己登录」这条路不存在。
- 但 `code` 只用于**首次换 token**。真正查余额时带的是业务 token/cookie。只要这个 token 能被抓出来、且有效期不是分钟级，就能离线复用。

于是结论收敛为：**抓包 → 看 token 能活多久、接口有没有额外签名。**

---

## 2. 三条路线对比（为什么选路线 A）

| | A. 服务端直连（选定） | B. 常驻安卓/模拟器自动点击 | C. 半自动 |
|---|---|---|---|
| 原理 | 复现 HTTPS 请求，带抓到的 token | 安卓上跑 uiautomator/无障碍脚本点小程序 | 系统只提醒，人工查完录入 |
| 能否上树莓派 | ✅ 完全可以 | ❌ 需要安卓设备常开 | ✅ 但价值有限 |
| 成本 | 低，一台 Pi | 中（一台安卓 + 一台 Pi） | 极低 |
| 微信版本更新影响 | 小（接口通常比 UI 稳定） | 大（UI 改版即失效，且微信会杀无障碍） | 无 |
| 功耗/稳定性 | 极低功耗，systemd 自启 | 需处理锁屏、断网、微信被杀 | 依赖人 |
| 合规观感 | 低频只读，最克制 | 自动化操作客户端，风险更高 | 无风险 |

路线 A 是唯一同时满足「树莓派」「长期无人值守」「低频克制」的选项。B 只能作为 A 失败时的兜底，且**必须放弃树莓派目标**。

---

## 3. 决策门（抓包后按结果分流）

抓完一次真实的「选楼栋 → 选房间 → 查余额」，按观察到的现象选择路径：

### G1 — 明文 JSON + 仅需 token/cookie

**现象**：请求头里有 `Authorization`/`token`/`Cookie`，请求 URL 里能看到楼栋号和房间号，响应是明文 JSON，字段里有一个金额和房间标识。
**结论**：路线 A 直接成立，树莓派完全可行。填 `client.py` 的 `HttpBalanceClient` 即可。
**后续**：记录 token 有效期；若 ≥ 数天，加 `refresh-token` 子命令定期人工续期。

### G2 — 需要微信态，但 token 有效期 ≥ 6 小时

**现象**：同 G1，但 token 有效期短，或每次要带 `openid` 之类只能在微信里拿到的字段。
**结论**：路线 A + 人工续期。`once` 检测到 401 时推送「token 过期，请续期」，用户在 PC 微信里重新打开小程序、抓一次新 token，执行 `refresh-token`。
**代价**：每 N 天人工介入 1 分钟。用户已表示「先跑通再说」。

### G3 — 请求带无法离线复现的签名

**现象**：请求体有 `sign`/`signature`/`timestamp`/`nonce`，且值在小程序 JS 里由**微信环境变量**（如 `wx.getStorageSync` 里的密钥、设备指纹）参与计算；或响应整体 AES 加密且密钥在 appservice 里动态下发。
**结论**：路线 A 不可行。转到：
- **B**：安卓真机常驻自动化（放弃树莓派）；
- **C**：半自动，系统只在你忘记时提醒。
此分支不在本次代码范围内，需重新评估。

### G4 — 房间可枚举且无需登录

**现象**：接口不校验身份，只要楼栋号+房间号。
**结论**：技术上最简单，但**仍然只查自己房间**（D8）。代码形态同 G1，只是不需要 token。

### 判定表

| 观察项 | G1 | G2 | G3 | G4 |
|---|---|---|---|---|
| 有 token/cookie | ✅ | ✅ | 可能 | ❌ |
| 有 sign/加密参数 | ❌ | ❌ | ✅ | ❌ |
| token 有效期长 | ✅ | ❌ | — | — |
| 能上树莓派 | ✅ | ✅（需人工续期） | ❌ | ✅ |

## 4. 这些部分没有风险

以下都已在本仓库实现并有测试覆盖，与学校接口无关：

- SQLite 幂等写入、按天聚合、告警去重；
- 日均消耗（中位数抗异常）、剔除充值跳变、剩余天数预测；
- Server酱 / PushPlus / SMTP 三个推送通道；
- Windows 计划任务与 systemd timer 两种调度；
- 纯标准库实现，Windows 与 Raspberry Pi OS Bookworm 行为一致。

## 5. 已识别的风险与对策

| 风险 | 概率 | 影响 | 对策 |
|---|---|---|---|
| 微信小程序加固（证书固定/加密） | 中 | 路线 A 不可行 | 决策门 G3；抓包时优先用安卓真机，JS 可用 wxapkg 解包 |
| token 短命 | 中 | 需频繁人工续期 | `refresh-token` + 过期推送；若 < 6h 则转 G3 |
| 学校接口或域名变更 | 中（低频） | 查询失败 | 失败即推送，不静默；改动集中在 `client.py` |
| 微信 PC 版更新导致抓包失效 | 低 | 仅影响再抓包 | 抓包只做一次，产物长期有效直到 token 过期 |
| 被判定异常访问 | 低 | 账号受限 | 每天 2 次 + 随机抖动 + 单房间 + 不复用他人凭证 |
| SD 卡写坏 | 低 | 数据丢失 | WAL + 每天 2 次写；建议定期 `cp electric.db` 备份 |
| 树莓派断网/断电 | 中 | 漏采 | systemd `Persistent=true` 补跑；告警带最后成功时间 |
| 学校有禁止性规定 | 未知 | 项目中止 | 只查本人、只读、不对外提供；发现明确禁止即停 |

## 6. 合规边界（硬约束）

1. 只查询**本人居住**的宿舍房间，不做任何房间枚举或批量扫描。
2. **只读**：不调用充值、支付、修改类接口。
3. 凭证只存本机 `config/secrets.toml`，不入库、不外发、不共享。
4. 频率每天 2 次，已远低于人为使用强度。
5. 抓包仅用于本人账号的协议分析；样本入库前脱敏。
6. 若发现学校有明确禁止自动访问的条款，立即停止并删除数据。
