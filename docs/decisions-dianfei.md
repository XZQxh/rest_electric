# 决策记录：宿舍电费自动查询系统

主题：`dianfei`。每条含**结论 + 理由**；未定的进「待定」。改动任何一条时在末尾补「变更记录」，不要直接覆盖旧结论。

日期：2026-10-21

---

## D1 数据入口

**结论**：微信小程序「上海海洋大学一卡通」（独立小程序窗口）是唯一能查宿舍电费余额的入口。学校办事大厅只能看到一卡通充值记录，看不到分寝室电费。

**理由**：用户确认。小程序内需先选楼栋、再选房间，页面只显示一个当前余额，没有历史用电量。

---

## D2 自动化路线

**结论**：抓到 token/cookie 后，在服务器侧直连后端接口；只有在签名/加密无法离线复现时才降级。

**理由**：登录链路是 `wx.login()` → 后端换 openid → 下发自家 token，`code` 只能由微信客户端生成。因此**全自动登录不可行**，只能复用已抓到的凭证。这是唯一能迁移到树莓派、无需常开一台安卓设备的路线。降级分支见 [feasibility.md](feasibility.md) 的决策门。

---

## D3 运行时：Python 3.11+ 纯标准库

**结论**：`urllib` + `sqlite3` + `tomllib` + `smtplib` + `zoneinfo`，不引入 requests/httpx/APScheduler 等任何第三方包。

**理由**：目标是树莓派 7×24 长期无人值守。零依赖意味着不会因为 pip 源不可达、Python 小版本升级、依赖冲突而半夜失效；迁移到 Pi 时直接拷目录即可。代价是要自己写几十行重试/超时封装，一次性成本。

---

## D4 存储：SQLite，金额以整数分

**结论**：单文件 SQLite，`balance_cents INTEGER`；启用 WAL 与 `synchronous=NORMAL`。

**理由**：单房间每天 2 条记录，SQLite 完全够用；单文件方便备份和拷走。金额用整数分避免浮点比较误差（`19.99 < 20` 这类判断不能出意外）。WAL 对每天 2 次写入的 SD 卡压力可忽略，且防止掉电时库损坏。

---

## D5 告警：固定阈值 + 预测欠费天数，取先触发

**结论**：`balance_cents < balance_floor_cents`（默认 2000 分 = 20 元）**或** `days_left < days_left_warn`（默认 3.0 天）时推送；同一 `(room_key, level, day)` 当天只推一次。

**理由**：固定阈值保底、不依赖历史数据；预测策略在积累几天数据后才生效，能提前预警而不只是事后报警。去重避免程序重试时刷屏。

---

## D6 推送通道：Server酱 / PushPlus

**结论**：主用 Server酱（`sctapi.ftqq.com`），备用 PushPlus（`pushplus.plus`），另外实现 SMTP 作为兜底；三者统一在一个接口后。

**理由**：用户选定微信接收。国内网络直连可达，树莓派上一个 POST 即可，无需代理。Telegram 在国内直连不可达，仅在已自备代理时作为可选项。

---

## D7 运行频率：每天 2 次，超低频

**结论**：09:07 与 21:07 各一次，程序内加 0–5 分钟随机抖动。

**理由**：电费账单以天为单位变化，查得更勤不增加信息量，只增加风控暴露面和服务器负担。抖动避免固定秒级特征。

---

## D8 查询范围：只查本人宿舍一个房间

**结论**：不做楼栋/房间枚举，不提供他人房间查询。

**理由**：合规红线。枚举房间号容易被判定为扫描，且明显超出「查自己电费」的合理范围。`room_key` 仅作为数据分区字段存在，为以后可能的扩展留位但不实现。

---

## D9 抓包方式

**结论**：Windows 上 mitmproxy + 系统代理 + 安装根证书；微信不认代理时用 Proxifier 强制 `WeChatAppEx.exe`。

**理由**：用户已同意安装根证书并修改系统代理，事后可一键卸载。这是唯一能提前验证可行性的手段。完整步骤见 [recon-sop.md](recon-sop.md)。

---

## D10 实施顺序：先侦察、后骨架，但骨架不等待侦察

**结论**：Phase 0 抓包与 Phase 1 骨架并行；骨架用夹具数据开发，协议相关逻辑全部收拢到 `client.py`。

**理由**：项目里唯一的技术未知就是接口能否离线复现，其余部分没有悬念。先把确定的 90% 写完测完，抓包结果只影响一个文件，避免为了未知而过度设计。

## 抓包实测结论（2026-10-22）

依据：mitmproxy 抓到的 8 条流量（`D:\EdgeDownload\flows (1)`）。

| 编号 | 待定项 | 结论 |
|---|---|---|
| T1 | 是否需要额外签名 | **不需要**。请求只有 `sw-Authorization` + 固定头，无 sign/nonce |
| T2 | 响应是否加密 | **否**，明文 JSON |
| T3 | token 有效期 | **2 小时**（JWT：iat 23:23:26 → exp 01:23:26，7200 秒） |
| T4 | 微信是否认系统代理 | **认**。开系统代理后小程序流量进入了 mitmproxy，无需 Proxifier |
| T5 | 是否有证书固定 | **无**。Python 直接重放成功 |
| T6 | 房间是否可枚举 | 请求体直接带 `roomid`/`buildid`，**可枚举**；仍坚持只查本人房间（D8） |
| T7 | 树莓派型号 | 仍未定 |

补充事实：

- **接口只在校园网可达**：`shoucard.shou.edu.cn` 解析到 `172.18.3.170`（内网地址）。树莓派必须接校园网或学校 VPN，否则查询必然失败。
- 后端是 Spring Boot + CAS 过滤器，异常时会回显完整堆栈（说明鉴权失败会以业务码/HTTP 错误暴露）。
- 服务端接受自定义请求头 `sw-Authorization: Bearer <JWT>`，UA 与 Referer 也一并复现。

## D11 接口协议（已固定）

**结论**：`POST https://shoucard.shou.edu.cn/openservice/miniprogram/queryroominfo`，请求体 `{"elcsysid":"1","areaid":"1","roomid":"11010610","buildid":"1"}`，响应 `data.restElecDegree` 为余额（元）。

**理由**：实测返回 200 与 24.1。字段已写入 `config/config.toml`，解析由配置驱动。

## D12 token 2 小时 → 全自动受阻（当前最大问题）

**结论**：token 是 JWT，有效期仅 2 小时，且响应里没有下发新 token（无滑动续期）。每天定时查询**无法**靠一个固定 token 完成，必须先解决续期。

**理由**：JWT 声明实测 `exp - iat = 7200s`。若后端登录只认 `wx.login()` 一次性 code，则服务端无法凭空换 token，全自动就走不通。

**已实测（2026-10-22，冷启动抓包 `flows (2)`，共 59 条流量）**：

认证链路是两条，都绕不开微信客户端：

```
第一次：POST /openservice/wechatauth/token {code:"<wx.login code>", stuempno:""}
        → retmsg "此用户未注册"
        → GET /openservice/sso/login?code=<同一个 code> → 302 到 uis.shou.edu.cn CAS
        → 用户在 CAS 页输入学号密码（captcha 为空、密码 RSA 加密、无 MFA）
        → CAS 302 带 ticket → /openservice/sso/auth → /openservice/sso/login?code=...
        → 之后 POST /openservice/wechatauth/token {code, stuempno:"<学号>"}
        → 成功，返回 JWT（TTL 仍是 2 小时）
```

**结论：纯服务器 / 纯树莓派方案不可行。** 实测证据：

| 尝试 | 结果 |
|---|---|
| 只用 CAS 会话 Cookie 查 queryroominfo | 403 Forbidden |
| 空 `code` + 学号 + CAS 会话换 token | `code:不能为空` |
| 复用旧 `code` + 学号 + CAS 会话 | `请求微信平台失败`（服务端去微信平台核验） |

即 `code` 是微信客户端实时生成的一次性凭证，服务端必须拿它向微信平台换取 openid。**没有任何办法在树莓派上凭空造出 code。**

CAS 登录本身是「可自动化」的（无验证码、RSA 密码、execution 表单令牌），但它产出的只是站点会话，查询接口不认。

**因此三条出路（需要用户选择，见下）**：

1. **常驻微信设备 + 自动捕获 token**：一台 24h 开机的设备（PC / 安卓手机 / 安卓模拟器）跑微信，定时用 UI 自动化打开小程序，本地 mitmproxy 抓 `wechatauth/token` 响应并自动写入 token；树莓派只负责查询、记账、告警。可全自动，但依赖 UI 自动化（微信更新易失效）。
2. **半自动**：用户每天打开一次小程序（本来也会看），`mitmproxy + scripts/import-flow.py` 一条命令更新 token，树莓派按小时/按天记录与告警。人工成本约 10 秒/天，最稳。
3. **放弃自动**：手工记录。

需要说明：前两条都需要一台常开的「微信设备」，**树莓派单独无法完成 7×24 无人值守**。

## D13 选定方案：半自动（2026-10-22）

**结论**：采用上面第 2 条路。用户每天打开 1–2 次小程序，`scripts/token_watcher.py`（mitmproxy 插件）自动把新 token 写入 `config/secrets.toml`；查询、记账、预测、告警、调度全部自动。

**理由**：
- 全自动专设备方案（安卓 UI 自动化）要额外一台常开设备，且微信改版即失效，投入大、稳定性差；
- 半自动额外的人工成本只有「打开一次小程序」，而用户本来也会看余额；
- 现有代码零改动即可用，今天就能开始积累历史数据。

**配套改动**：
- `start-mitmweb.ps1` + `token_watcher.py`：打开小程序即刷新 token，无需命令；
- 新增 `python -m rest_electric token-status`：本地看 token 剩余时间；
- 登录失效告警冷却由 7 天改为 1 天（与 2 小时 token 匹配）。

**代价（明确接受）**：每天需要人工打开小程序 1–2 次；token 过期期间的定时查询会失败并推送续期提醒。

**未来若想升级到全自动**：保留本方案作为兜底，再评估安卓设备方案（见 D12 第 1 条）。

## D14 主通道改为「手机读屏 + 树莓派接收」（2026-10-22 下午）

**结论**：不再以 token 为采集前提。用一台闲置安卓手机（小号微信）定时打开小程序，
用无障碍读页面上的余额，POST 给树莓派的 `serve-ingest` 落库；D13 的 token 半自动降级为兜底。

**理由**：
- token 的 2 小时 TTL 与「服务器造不出 code」是死结（D12 已实测），继续在 token 上投入没有边际收益；
- 采集真正需要的只是那个数字；手机每次重新查询时小程序自己会换 token，系统完全不参与；
- 家里有常开的树莓派，适合做落库/预测/告警；手机只当"眼睛"，功耗与逻辑都最轻。

**代价**：
- 需要一台常开的安卓机 + 小号微信。小号要重新绑定学号，存在覆盖主号 openid 绑定的风险，
  验证步骤见 [phone-automation.md](phone-automation.md) 的 G1；
- 微信 UI 改版会让读屏脚本失效——失效必须告警，不能静默。

**配套改动**：新增 `ingest.py`、`serve-ingest` / `ingest` / `check-stale` 三个命令、
`[ingest]` 配置与共享密钥、接收器与离线检查的 systemd 单元；
部署脚本默认停用每天两次的直连查询定时器（`--with-once-timer` 可保留）。

## D15 主通道改为网页版 `/epay/h5/eleresult`（2026-10-22 傍晚）

**结论**：采集改走办事大厅背后的网页端查询页，`api.mode = "epay"`：
`GET /epay/h5/eleresult?sysid=1&roomid=..&areaid=1&buildid=1`，未登录时自动走 CAS
（学号+密码，RSA 加密，无验证码），从 HTML 里读「剩余电量 xx度」。

**理由**：
- 这条链路不经过微信：没有 `wx.login()`、没有一次性 `code`、没有 2 小时 JWT；
- 服务端渲染 HTML，一个 GET 就够，Pi 上纯标准库能实现；
- 学校 1 度 = 1 元，入库口径与之前一致，预测/阈值/报表都不用改；
- 已在真实浏览器里验证：能出余额，充值流程也正常（说明会话是真的）。

**代价**：
- Pi 上要存统一身份认证的学号与密码（`secrets.toml` 600，仅本机）；
- 学校若加验证码或改页面结构，脚本会失败——失败必须告警，不能静默；
- 该接口是"给网页用的"，不是公开 API，学校随时可能改。

**配套改动**：新增 `epay.py`（RSA + CAS 登录 + HTML 解析 + Cookie 复用）、
`[epay]` 配置与密钥、`api.mode = "epay"`；`rest-electric.timer` 改为白天每 2 小时一次；
手机上报通道（D14）降级为备用。
